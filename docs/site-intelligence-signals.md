# Site Intelligence Signals Layer

This layer sits above the Site Asset Master and below the future Action Queue. Its job is to normalize external and first-party observations onto stable `assetId` values without pretending that every observation is equally mature.

## Source-of-truth boundaries

- GitHub content metadata and registries define asset identity, module/roadmap placement, Owner keywords, canonical paths, tools, diagnostics, and API hubs.
- User-supplied Google Search Console exports define Google search performance observations. The signals layer consumes the JSON generated by `search-console-opportunity-report.mjs`; it does not fetch private GSC data.
- Neon defines first-party behavior and Runtime Evidence: internal search, tool events, article feedback, and verification evidence.
- The signals layer is read-only. It does not mutate content, Neon rows, Search Console, or production routes.

## What is normalized

Each observation is retained as a signal with:

- `source`
- `kind`
- `assetId` when it can be mapped
- optional `relatedAssetId` for relationships such as a GSC Owner mismatch
- `sampleGate`
- `rankingEligible`
- raw evidence payload

Unmapped observations are retained in `unmappedSignals`; they are never silently dropped.

## Behavioral sample gate

Internal search, tool usage, and article feedback use a conservative operational minimum of 20 observations per source before they can be marked `eligible-for-ranking`.

Below 20 observations they remain `observe-only`.

This is an internal safety gate, not a statistical confidence claim. It exists to prevent a handful of early events from pushing an asset to the top of a future optimization queue.

Runtime Evidence is different: accepted/rejected/revoked evidence is direct technical evidence, not a popularity sample. It is therefore marked `direct-evidence`, but it still does not independently create SEO priority in this layer.

Google Search Console classifications preserve the upstream report's P0/P1/P2 classification. The signals layer does not invent a second GSC score.

## No composite score yet

This phase deliberately does not calculate:

- SEO Opportunity Score
- Content Health Score
- Evidence Health Score
- User Demand Score
- Maintenance Priority

Those belong in the next decision layer after signal coverage and sample maturity are sufficient.

## Generate a report

With a user-supplied Search Console JSON and Neon available through `DATABASE_URL`:

```bash
node scripts/site-intelligence-signals-report.mjs \
  --gsc reports/search-console-opportunities.json \
  --days 30 \
  --json reports/site-intelligence-signals.json \
  --markdown reports/site-intelligence-signals.md
```

Without `DATABASE_URL`, the report still works with GSC-only signals. Without `--gsc`, it can generate a Neon-only snapshot.

## Vercel budget rule

Repository work for linqingan.com follows this delivery rule:

1. Analyze the full change boundary before pushing a feature branch.
2. Prepare all related files, checks, fixtures, and documentation together.
3. Run syntax/pure-logic validation before the first branch push whenever possible.
4. Push one coherent change set to trigger one Preview build.
5. If CI or Preview fails, inspect all available failures first, batch the fixes, and push one consolidated correction.
6. Do not use Vercel Preview as a file-by-file development debugger.

Vercel remains the final deployment-environment verification layer, not the first feedback loop.

## Next layer

The future Action Queue should consume this normalized snapshot plus Asset Master metadata. It may rank actions only when the source-specific gates allow it, and it must keep the reason, source, and raw evidence traceable for every recommendation.
